that does voice-fingerprint / fraud scoring. It must be deployed and reachable, and
the Next app pointed at it via `ANALYSIS_SERVICE_URL`.

## Demo datasets (hdfc-creditfraud, yesbank-cards) — DEPLOY DATA REQUIRED

The fraud (`hdfc-creditfraud`, "Credit Risk") and cards (`yesbank-cards`, "Credit
Cards") datasets read CSVs from `data/csv/<id>/`, which are **gitignored**
(local-only, like every other dataset's data). On a fresh deploy the repo has the
configs but NOT the data, so `read_csv` throws on first query and the dataset is
non-functional until the data is provisioned.

**On deploy (e.g. demo.actioneer.com), copy the generated CSVs to the box:**

```bash
# generated by ~/projects/actioneer-demo-data
cp -r ~/projects/actioneer-demo-data/out/HDFC_CreditFraud_Demo/*.csv data/csv/hdfc-creditfraud/
cp -r ~/projects/actioneer-demo-data/out/YesBank_Cards_Demo/*.csv     data/csv/yesbank-cards/
```

On first query the app builds `data/<id>.duckdb` from the CSVs (materializing
`transactions`, `statements`, `fraud_alerts`/`campaign_history`, `card_spend_stats`,
and the `fraud_call_context` enrichment view the voice fraud routes read). This is
one-time per server; the tables persist in the `.duckdb` file. Bump `setupVersion`
in the dataset config whenever the CSV schema changes so the materialized tables
rebuild.

Hero fraud cases on the alerts dashboard are pinned to specific CRITICAL alert IDs
in `src/app/api/fraud-alerts/route.ts` (`HERO_ALERT_IDS`). Regenerating the demo
data changes alert IDs — repick from `fraud_call_context WHERE severity='CRITICAL'`.

**Maintenance notes:**
- These two datasets materialize some tables (`transactions`, `statements`,
  `fraud_alerts`/`campaign_history`, `card_spend_stats`, `fraud_call_context`).
  Materialized tables are built "if missing", so bumping `setupVersion` alone does
  NOT rebuild an existing `.duckdb`. After a CSV-schema change, **delete the local
  `data/<id>.duckdb`** so it rebuilds (fresh deploys are unaffected — they build
  from scratch). Note: if a stale `.duckdb` has `fraud_alerts`/`campaign_history`
  as a *view* (pre-materialization), it must be deleted, not upgraded in place.
- `card_spend_stats.avg_amt_90d`/`p95_amt_90d` are named for the voice route's
  expected schema but computed over the card's full purchase history, not 90 days.
- These datasets have no handcrafted sample-workspace seeder (segments/playbooks),
  same as the global `SEED_SAMPLE_WORKSPACE_CONTENT=false` state. They work fully
  for analytics + voice; only the auto-seeded starter workspace is absent.
