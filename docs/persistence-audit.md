**Date:** 2026-03-31

## Storage Architecture Overview

The app uses 4 storage tiers:

| Tier | Technology | Survives Refresh? | Survives Deploy? | Examples |
|------|-----------|-------------------|-------------------|----------|
| **In-memory** | JS Maps, Sets, module globals | NO | NO | metric-store, knowledge-store, forecast-store, approval-store |
| **localStorage** | Browser Web Storage (5MB) | YES | YES | folders, credits, saved-charts, onboarding, sidebar state |
| **SQLite** | better-sqlite3 (WAL mode) | YES | YES (if volume mounted) | conversations, boards, playbooks, segments |
| **Filesystem** | JSON files in /data/ | YES | DEPENDS on Railway volume | dataset configs, schema-maps, metrics.json, uploaded CSVs |

## Critical Persistence Issues

### 🔴 Issue 1: Railway Ephemeral Filesystem Kills Uploaded Datasets

**Problem:** On Railway redeploy, the container is recreated. Everything in `/data/datasets/` is lost unless a Volume is mounted at that path.

**What's lost:**
- All uploaded CSV/DuckDB files
- All config.json, schema-map.json, metrics.json, knowledge.json
- User's dataset appears to vanish — dynamic-registry loads empty list

**Current state:** Railway volume is mounted at `/app/data` but the docs suggest user datasets may need a separate volume at `/app/data/datasets`.

**Impact:** Client uploads data, demos it, you redeploy a fix, their data is gone.

### 🔴 Issue 2: Folders Are localStorage-Only (No Server Persistence)

**Problem:** Conversation folders exist ONLY in localStorage. No server backup, no SQLite storage.

- `folder-store.ts` writes to `baby-sentinel-folders` in localStorage
- No `/api/folders` endpoint exists
- No migration path to server
- Clearing browser cache or switching devices = all folders gone

**Impact:** Folder organization is device-specific and fragile.

### 🔴 Issue 3: Credits Are localStorage-Only (No Server Persistence)

**Problem:** Credit balance and transaction history exist ONLY in localStorage.

- `credit-store.ts` writes to `baby-sentinel-credits`
- No server-side credit ledger API
- Clearing cache = credits reset to seed state (453 credits)

**Impact:** If this is shown to clients as a real feature, credits reset randomly.

### 🔴 Issue 4: Saved Charts Are localStorage-Only

**Problem:** Saved explorer chart configs in `sentinel-saved-charts` — no server backup.

- `saved-chart-store.ts` has no server sync
- No quota handling (silent fail on write)
- Switching browsers = charts gone

### 🟠 Issue 5: Forecast Seed Data Is Ephemeral

**Problem:** `forecast-store.ts` is in-memory only. User-edited forecast parameters are lost on page refresh.

- No localStorage fallback
- No server persistence
- Reverts to `BASE_SEED_DATA` hardcoded defaults

### 🟠 Issue 6: localStorage Quota Pressure

**Worst case breakdown (5MB browser limit):**

| Category | Estimated Size |
|----------|---------------|
| Conversations (cache) | 500KB–3MB (unbounded messages) |
| Board cards (5 boards × 30 cards) | 750KB–3.75MB |
| Playbooks (10 with run history) | 500KB–1.5MB |
| Credits + folders + charts + misc | 200KB–500KB |
| **Total** | **2MB–8.75MB** |

**When quota is exceeded:**
- Board store: catches QuotaExceededError → purges stale boards → retries
- **All other stores: silently fail** — data not written, no user notification
- Conversation/playbook writes fail silently but server write (sendBeacon) still attempts

**Unbounded growth risks:**
- `conversation-store`: No message limit per conversation. 100+ message chats = 100-500KB each.
- `playbook-store`: `runHistory` array appends indefinitely. 10 playbooks × 50 runs = 1.5MB.

### 🟠 Issue 7: Version Mismatch Nukes All Data for That Store

Every versioned store (boards v13, conversations v2, playbooks v2, folders v1, credits v2) checks version on init. **Mismatch = localStorage.removeItem() for the entire key.**

- If you bump board store to v14 in a deploy, ALL board localStorage data is wiped
- Recovery depends on server having the data (works for boards/conversations/playbooks, does NOT work for folders/credits/charts)

### 🟡 Issue 8: Debounced Writes Can Lose Recent Changes

| Store | Debounce | Risk Window |
|-------|----------|-------------|
| credit-store | 300ms | 300ms of credit transactions |
| folder-store | 300ms | 300ms of folder changes |
| playbook-store | 300ms local, 1000ms server | 1s of playbook edits |
| conversation-store | 2000ms server | 2s of chat messages |

**Mitigation:** `beforeunload` + `visibilitychange` handlers flush via `sendBeacon()`. But `sendBeacon` can fail silently, and tab crashes skip unload handlers entirely.

## Hybrid Persistence Pattern (What Works Well)

Three stores have good dual-persistence: **conversations, boards, playbooks**.

```
Init:
  1. Read localStorage (fast, immediate render)
  2. Background: fetch from server (source of truth)
  3. Server data overwrites localStorage
  4. If server empty + localStorage has data → migrate to server

Write:
  1. Update in-memory Map
  2. Debounced write to localStorage
  3. Debounced write to server API
  4. On unload: flush + sendBeacon fallback
```

This is solid — but folders, credits, saved charts, and forecast data are NOT part of this pattern.

## Data Flow: What Happens On...

### Page Refresh
| Data | Outcome |
|------|---------|
| Conversations | ✅ Restored from server (localStorage as fast cache) |
| Boards + cards | ✅ Restored from server |
| Playbooks | ✅ Restored from server |
| Segments | ✅ Restored from SQLite |
| Folders | ⚠️ Restored from localStorage only |
| Credits | ⚠️ Restored from localStorage only |
| Saved charts | ⚠️ Restored from localStorage only |
| Metrics | ✅ Rebuilt from API (server reads metrics.json) |
| Knowledge | ✅ Rebuilt from API |
| Forecast edits | ❌ LOST — reverts to defaults |
| Explorer config | ❌ LOST — resets |
| Pending approvals | ❌ LOST — resets |

### Server Restart / Redeploy
| Data | Outcome |
|------|---------|
| SQLite data | ✅ Persists (if volume mounted) |
| Uploaded datasets | ❌ **LOST if no volume at /data/datasets** |
| Built-in DuckDB files | ✅ Rebuilt from parquet/CSV by startup script |
| In-memory caches | ❌ Rebuilt lazily on first request |

### Browser Cache Clear
| Data | Outcome |
|------|---------|
| Conversations | ✅ Re-fetched from server |
| Boards | ✅ Re-fetched from server |
| Playbooks | ✅ Re-fetched from server |
| Folders | ❌ **GONE — no server backup** |
| Credits | ❌ **GONE — resets to seed** |
| Saved charts | ❌ **GONE — no server backup** |
| Onboarding progress | ❌ GONE — wizard restarts |
| Dataset/model selection | ❌ Resets to defaults |

### User Switches Device/Browser
| Data | Outcome |
|------|---------|
| Server-backed data | ✅ Available (conversations, boards, playbooks, segments) |
| localStorage-only data | ❌ Not available (folders, credits, charts, onboarding) |

## localStorage Keys by Size Risk

| Risk | Key Pattern | Growth | Mitigation |
|------|-------------|--------|-----------|
| HIGH | `baby-sentinel-conversations` | Unbounded (messages accumulate) | Server is source of truth; can be cleared |
| HIGH | `baby-sentinel-playbooks` | Unbounded (runHistory appends) | Server is source of truth; can be cleared |
| MEDIUM | `baby-sentinel-board-cards-{id}` | 30 rows × N cards × M boards | Trimming + stale board purge |
| LOW | `baby-sentinel-credits` | Transactions append | Mock data; bounded by session length |
| LOW | All others | Fixed or small | No concern |

**Board store's aggressive cleanup (the only store that handles quota):**
1. `purgeStaleBoards()` — removes boards with 0 cards
2. `clearLegacyStorage()` — removes deprecated keys + conversation cache (rebuildable from server)
3. Retry write after cleanup

## Recommendations Summary

### Must Fix for Client Demos

1. **Ensure Railway volume covers `/data/datasets/`** — uploaded data must survive redeploys
2. **Move folders to SQLite** — add `folders` table to meta-db, same pattern as segments
3. **Move credits to SQLite** — or hide credit feature if it's mock-only
4. **Move saved charts to SQLite** — or at minimum add server sync
5. **Add conversation message limit** — cap at N messages in localStorage to prevent quota exhaustion
6. **Add playbook runHistory limit** — cap at last 50 runs
7. **Remove LIMIT 500 from auto-generated segment SQL** — misleading user counts

### Nice to Have

8. Persist forecast seed data to localStorage or server
9. Add quota monitoring — warn user when localStorage is >80% full
10. Add explicit "your data is saved" indicators in UI
11. Surface enrichment status to users (not silent fire-and-forget)
