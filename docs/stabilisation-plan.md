**Date:** 2026-03-31
**Goal:** Make the product stable, persistent, and fully functional for uploaded datasets — no feature gaps, no data loss, no silent failures in front of clients.

### B. LIMIT 500 on Auto-Generated Segments

The LLM prompt (`src/lib/prompts/segments.ts:46`) forces `LIMIT 500` on all auto-generated segment SQL. But the user count is computed by stripping the LIMIT via regex:

```typescript
// generate-all/route.ts:98
sql.replace(/\s*LIMIT\s+\d+\s*$/i, "")
```

Result: Segment card says "12,847 users" but the actual SQL only matches 500. Every downstream feature (composition, overlap, users tab, explorer filtering) operates on the truncated set. **Silently wrong data shown to clients.**

### C. Data That Doesn't Persist

| Data | Current Storage | Dies On |
|------|----------------|---------|
| Conversation folders | localStorage only | Cache clear, new device, new browser |
| Credits & transactions | localStorage only | Cache clear, new device |
| Saved explorer charts | localStorage only | Cache clear, new device |
| Forecast seed edits | In-memory only (no persistence at all) | Page refresh |
| Uploaded dataset files | Filesystem `/data/datasets/` | Railway redeploy (if volume misconfigured) |

### D. localStorage Quota Pressure (5MB Browser Limit)

| Store | Growth Pattern | Risk |
|-------|---------------|------|
| Conversations (`baby-sentinel-conversations`) | Messages accumulate without limit | 500KB–3MB |
| Playbooks (`baby-sentinel-playbooks`) | `runHistory` appends forever | 500KB–1.5MB |
| Board cards (`baby-sentinel-board-cards-{id}`) | 5 boards × 30 trimmed cards | 750KB–3.75MB |

When quota is exceeded: **only board-store catches QuotaExceededError** (purges stale boards, retries). All other stores silently fail — writes don't happen, no user notification.

Version bumps (boards is at v13) wipe all localStorage for that store. Boards/conversations/playbooks recover from server. **Folders/credits/charts do NOT recover — they're gone.**

### E. DuckDB & Upload Architecture

**Current:** Uploaded CSVs stay on disk. DuckDB creates views (`SELECT * FROM read_csv(...)`) that read CSV lazily on every query. Both CSV and `.duckdb` file must exist. Slower queries.

**Better:** Import CSVs into DuckDB tables (`CREATE TABLE AS SELECT FROM read_csv(...)`). Single self-contained `.duckdb` file. 3-10x faster queries. Delete CSVs after import.

Change fallback from `₹` to `$` (safer default for demos). Or better: if currency is undefined, show no currency symbol rather than a wrong one.

#### 1d. Auto-trigger metric generation on upload (1 hour)

**File:** `src/app/api/datasets/upload/route.ts`

The enrichment pipeline can generate metrics. The upload route just doesn't call it. Add the call after enrichment completes so users see metrics immediately.

#### 1e. Add event auto-generation to enrichment (1 day)

**New file:** `src/lib/datasets/event-generator.ts`
**Modified:** `src/lib/datasets/schema-enricher.ts`, `src/lib/datasets/dynamic-registry.ts`

**Algorithm (no LLM needed for basic events):**

The schema-map already profiles every column (cardinality, semantic type, sample values). One new enrichment step:

**Step 1 — Table-level events:** Every table becomes a base event.
```typescript
{ id: "orders", displayName: "Orders", table: "orders", properties: [...] }
```

**Step 2 — Event-type column detection:** Find VARCHAR columns named like `event_type`, `event_name`, `action`, `type`, `status` with cardinality between 3–50. For each distinct value:
```typescript
{ id: "orders_purchase", displayName: "Purchase", table: "orders",
  filterColumn: "event_type", filterValue: "purchase", properties: [...] }
```

**Step 3 — Properties:** String columns with low/medium cardinality (already in schema-map) become `EventProperty` items for breakdown/filtering.

**Step 4 — Value columns:** Numeric columns (revenue, amount, price) become `valueColumn` for sum/average measures.

**Step 5 — Date column:** Use `dataset.dateField` as default, or detect the first TIMESTAMP/DATE column per table.

**Storage:** Save to `/data/datasets/<id>/events.json`. Load in `dynamic-registry.ts` alongside other enriched fields:
```typescript
if (existsSync(eventsPath)) {
  raw.events = JSON.parse(readFileSync(eventsPath, "utf-8"));
}
```

**Result:** Explorer, Funnel, and Retention tabs work on uploaded datasets.

### Phase 2: Make Everything Persist (~2 days)

#### 2a. Verify Railway volume covers /data/datasets/ (5 min)

#### 2b. Switch CSV uploads to DuckDB import (3 hours)

**File:** `src/app/api/datasets/upload/route.ts`

Change:
```typescript
// FROM (current — lazy view):
CREATE OR REPLACE VIEW ${tableName} AS SELECT * FROM read_csv('${filePath}')

// TO (materialized import):
CREATE TABLE IF NOT EXISTS ${tableName} AS SELECT * FROM read_csv('${filePath}', AUTO_DETECT=TRUE)
CHECKPOINT  // flush WAL → everything in .duckdb file
// then delete the CSV (optional, saves storage)
```

Benefits:
- One file to persist per dataset (`.duckdb` only)
- 3-10x faster queries (columnar vs CSV scan)
- No parquet conversion needed — DuckDB's internal format is already columnar
- Multi-CSV uploads naturally become multiple tables in one `.duckdb`

Update `config.json` schema: `sourceFiles` becomes metadata-only (no longer needed at runtime).

### Phase 3: Deep Research Quality Parity (~1.5 days)

The quality gap between sample and uploaded datasets comes from three specific fields: `agents` (structured AgentSpec[]), `queryDescriptions` (per-agent query lists), and `domainHints` (SQL gotchas). Sample datasets have hand-crafted versions with 15+ rules and specific column references. Uploaded datasets get LLM-generated versions with 3-6 generic rules.

**Root cause:** The LLM enrichment sees schema + 5 sample rows and generates syntactic hints (quoting, date parsing). Hand-crafted hints encode runtime knowledge — cross-column correlations, impossible filter combinations, table size warnings, data range constraints.

**The fix is better profiling + better prompts, not a different architecture.**

#### 3a. Cross-column profiling queries (3 hours)

**Files:** `src/lib/datasets/data-profiler.ts`, `src/lib/datasets/schema-enricher.ts`

Add SQL-based profiling queries that run against the actual data before the LLM enrichment step:

```sql
-- 1. Table size warnings (which tables to avoid scanning directly)
SELECT COUNT(*) FROM each_table

-- 2. Date range detection
SELECT MIN(date_col)::VARCHAR, MAX(date_col)::VARCHAR FROM primary_table

-- 3. Cross-column correlations (impossible filter combinations)
-- e.g., discovers "channel='apple_search_ads' only appears with platform='IOS'"
SELECT DISTINCT col_a, col_b FROM table
WHERE col_b IN (top_5_values) LIMIT 100

-- 4. Value distribution skew
-- e.g., discovers "95% of rows are status='active'"
SELECT col, COUNT(*) as cnt FROM table
GROUP BY col ORDER BY cnt DESC LIMIT 20

-- 5. Column co-occurrence nullity
-- e.g., discovers "result IS NULL when level_type IN ('FreeDrive','Multiplayer')"
SELECT col_a IS NULL AND col_b IS NOT NULL as pattern, COUNT(*) FROM table GROUP BY 1
```

**Cost:** 5-10 SQL queries per table. DuckDB executes each in <1s on imported data. Total: 5-30 seconds per dataset.

**Result:** The LLM now has the same operational knowledge a human analyst would have after 30 minutes of data exploration.

#### 3b. Two-pass enrichment (2 hours)

**File:** `src/lib/datasets/schema-enricher.ts`

Currently enrichment is one pass: profile → analyze → generate. Make it two passes:

**Pass 1 (existing):** Profile columns, detect types, generate initial schema context.

**Pass 2 (new):** Run the cross-column profiling queries from 3a. Feed Pass 1 results + Pass 2 profiling results back to the LLM with a refined prompt:

```
You previously analyzed this dataset and detected it as "{domain}".
Here are runtime profiling results:
- Table sizes: orders (2.3M rows), products (500 rows), users (45K rows)
- Date range: 2024-03-01 to 2025-01-15
- Cross-column patterns: [channel='apple_search_ads' → platform='IOS' only]
- Skewed columns: [status: 95% 'active'] [country: 60% 'US']
- NULL patterns: [result IS NULL when level_type IN ('FreeDrive','Multiplayer')]

Now generate IMPROVED domainHints that include:
1. Table size warnings (which tables to avoid scanning directly)
2. Date range constraints (what ranges return data)
3. Impossible filter combinations discovered above
4. Skewed columns that shouldn't be filtered without reason
5. NULL patterns that affect aggregations
```

**Cost:** One additional LLM call (~2s) + the profiling queries. Total enrichment goes from ~60s to ~90s.

#### 3c. Better agent query prompts + validation (2 hours)

**File:** `src/lib/prompts/dataset-enrichment.ts`

Current prompt produces generic agent queries:
```typescript
// LLM-generated (current):
{ hint: "GROUP BY key dimensions" }
{ hint: "Aggregate primary value metrics" }

// Hand-crafted (target):
{ hint: "cac_by_channel GROUP BY channel, os — compare iOS vs Android CPI" }
{ hint: "roas_by_cohort — roas_d30 = total_ltv_d30 / cpi, values > 1.0 = positive" }
```

**Fix:** Change the prompt to demand specific column references:

```
MANDATORY: Every hint MUST reference actual column names from the schema above.
Bad:  { hint: "GROUP BY key dimensions" }
Good: { hint: "GROUP BY channel, platform — from orders table" }
```

Add a validation step in `generatePrompts()`: reject any agent query whose `hint` doesn't contain at least one column name from the schema. Re-prompt once if validation fails.

#### 3d. Example queries in schemaContext (1 hour)

**File:** `src/lib/prompts/dataset-enrichment.ts`

Add to the annotatedSchemaContext prompt: generate 2-3 example SQL queries per table. The downstream SQL generation LLM sees correct query patterns:

```
TABLE: orders (2.3M rows)
  - order_id     VARCHAR  -- unique order identifier
  - customer_id  VARCHAR  -- FK to users.id
  - order_date   DATE     -- 2024-03-01 to 2025-01-15
  - total_amount DOUBLE   -- order total in USD
  - status       VARCHAR  -- 'completed' (82%), 'pending' (10%), 'cancelled' (8%)

EXAMPLE QUERIES:
  Daily revenue: SELECT order_date, SUM(total_amount) FROM orders WHERE status='completed' GROUP BY 1
  Top customers: SELECT customer_id, SUM(total_amount) FROM orders GROUP BY 1 ORDER BY 2 DESC LIMIT 20
```

#### 3e. Testing across uploaded datasets (2 hours)

Upload 3-4 different CSVs (ecommerce, fintech, gaming, SaaS) and verify:
- domainHints include data range, table size warnings, impossible combinations
- Agent queries reference actual column names
- schemaContext includes example queries
- Deep research produces focused SQL with correct column references

#### Quality comparison: before vs after

**domainHints:**

| Aspect | Before (LLM, 3-6 rules) | After (profiled + LLM, 10-15 rules) | Hand-crafted (15+ rules) |
|--------|--------------------------|--------------------------------------|--------------------------|
| Column quoting/parsing | ✅ | ✅ | ✅ |
| Date range constraints | ❌ | ✅ (from MIN/MAX query) | ✅ |
| Table size warnings | ❌ | ✅ (from COUNT query) | ✅ |
| Impossible filter combos | ❌ | ✅ (from cross-column query) | ✅ |
| Value distribution skew | ❌ | ✅ (from GROUP BY query) | ✅ |
| Business domain rules | ❌ | ❌ | ✅ |

**Agent queries:**

| Aspect | Before | After | Hand-crafted |
|--------|--------|-------|--------------|
| References real columns | Sometimes | Always (validated) | Always |
| SQL fragment in hint | Generic template | Specific GROUP BY/WHERE | Specific with table names |
| Domain-relevant focus | Broad | Data-driven | Expert-tuned |

**The remaining ~5-10% gap** is business-domain knowledge that isn't in the data: "commission rates vary by service_tier: premium 30-32%", "NPS scores: promoters 9-10, passives 7-8, detractors 0-6". A human analyst learns these from domain experts. The LLM can't infer them from column stats. **This gap doesn't matter for demos** — it means slightly less efficient SQL or slightly less focused questions, but correct answers.

## Architecture After Fixes

### Storage (fully persistent)

```
SQLite (sentinel-meta.sqlite)
├── conversations (messages, tags, folders)
├── boards + board_cards + board_sections + board_connections + board_frames
├── playbooks (v1 + v2)
├── segments (SQL, push_status)
├── folders          ← NEW
├── saved_charts     ← NEW
├── credits          ← NEW
├── forecast_seeds   ← NEW

Filesystem (/data/datasets/ — Railway volume)
├── <dataset-id>/
│   ├── <id>.duckdb         ← self-contained (imported tables, no CSV dependency)
│   ├── config.json         ← dataset metadata
│   ├── schema-map.json     ← enrichment output
│   ├── metrics.json        ← auto-generated metric definitions
│   ├── events.json         ← NEW: auto-generated event definitions
│   └── knowledge.json      ← on-demand knowledge entries
```

### Upload Flow (after fixes)

```
User uploads orders.csv, users.csv, products.csv
    ↓
Stream to temp dir via busboy (50MB/file limit)
    ↓
Create /data/datasets/<id>/<id>.duckdb
    ↓
For each CSV:
  CREATE TABLE <name> AS SELECT * FROM read_csv('<path>', AUTO_DETECT=TRUE)
  CHECKPOINT
    ↓
Delete temp CSVs (data now in .duckdb)
    ↓
Run schema enrichment (3-step LLM pipeline):
  1. Profile tables (columns, types, cardinality, samples)
  2. Analyze columns (semantic types, descriptions, SQL gotchas)
  3. Generate prompts (agents, domain hints, suggested prompts, persona)
    ↓
NEW: Generate events from schema-map (mechanical, no LLM)
  → events.json saved to dataset dir
    ↓
Generate metrics from schema (existing, just auto-triggered now)
  → metrics.json saved to dataset dir
    ↓
Save config.json (atomic write)
    ↓
Dataset immediately available:
  ✅ Chat works (agents, prompts, persona all generated)
  ✅ Explorer works (events auto-generated)
  ✅ Segments work (SQL generation has domain hints)
  ✅ Metrics page populated (auto-generated)
  ✅ Boards work (chart inference has dataset context)
```

### Client Store Pattern (after fixes)

All user data follows the same hybrid pattern:

```
                 ┌──────────────┐
                 │  In-Memory   │  ← Fast reads/writes
                 │  (Map/Set)   │
                 └──────┬───────┘
                        │ debounced
            ┌───────────┴───────────┐
            ▼                       ▼
    ┌──────────────┐       ┌──────────────┐
    │ localStorage │       │  Server API  │  ← Source of truth
    │ (fast cache) │       │  (SQLite)    │
    └──────────────┘       └──────────────┘
            │                       │
            └───── beforeunload ────┘
                   sendBeacon
                   flush pending
```

Survives: page refresh ✅ | cache clear ✅ | device switch ✅ | Railway redeploy ✅
