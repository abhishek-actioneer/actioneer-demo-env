# Behavioral Segments Card Gallery & Profile Detail

## Overview

Evolve the existing `/segments` page to feature a **visual card gallery** of LLM-generated behavioral segments above the existing manual segments table. Each behavioral segment has a personality (name, description, traits, accent color) generated by the segmentation engine. Clicking a card opens a **profile-first detail view** showing behavioral identity then performance metrics. Users can push segments to integrations or ask follow-up questions about a segment via chat.

Frontend only. The backend segmentation engine is assumed to exist. All behavioral data is mock-seeded for prototype.

## Problem Statement / Motivation

The current segments experience is purely manual: users write SQL or describe a segment in natural language, and the system creates a query-based segment. There is no way to **discover** behavioral clusters that already exist in the data. The SIMS Mobile approach (PCA + k-means + profiling) produces segments with personality and narrative, which are far more actionable for product and ad creative strategy than raw SQL filters.

## Technical Approach

### Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Data model | Add optional fields to `SegmentDisplay` | Avoids type union complexity; presence of `behavioralTraits?.length > 0` is the discriminator |
| Mock data location | Merged into existing `MOCK_SEGMENTS` array in `mock-segments.ts` | Detail page lookup checks `MOCK_SEGMENTS` first — behavioral mocks must be in this array |
| ID convention | `behavioral-` prefix (not `mock-`) | Avoids the `mock-` guard in push-to-integration flow |
| Accent colors | Hex strings via inline `style={{}}` | Per MEMORY.md: never use Tailwind arbitrary values with CSS variables |
| Gallery layout | Responsive grid (2-3-4 cols) | Better than horizontal scroll for discoverability; works at any count |
| Gallery vs table | Behavioral segments in gallery only, not duplicated in table | Keeps the two experiences visually distinct; avoids field-mapping burden |
| Search scope | Table search filters manual segments only; gallery has no search | Gallery will have 4-6 segments max in prototype — search is unnecessary |
| Detail page sections | Behavioral profile + metrics replace SQL/refresh/sample-users for behavioral type | SQL and refresh are meaningless for behavioral segments |
| "Ask about this segment" | `router.push("/?segment={id}")` + `sessionStorage` for context | URL param triggers context injection on chat page mount |
| Push behavior | Mock success (1.5s delay → synced) same as existing | Prototype behavior; push semantics for behavioral segments are a backend concern |
| Sidebar panel | Combined pool (behavioral + manual), behavioral segments first | Behavioral segments get priority; `max 8` shared across both types |
| Performance metrics | Static mock data per segment | No real computation; values are hardcoded in mock data |

### Data Model Extensions

**File: `src/lib/types.ts`**

Add optional fields to `SegmentDisplay`:

```typescript
export interface SegmentDisplay extends Segment {
  // ... existing fields ...

  // Behavioral segment fields (optional — presence = behavioral type)
  behavioralTraits?: string[];        // e.g. ["High spend", "Multi-category", "Quick conversion"]
  behavioralSummary?: string;         // LLM-generated narrative description
  accentColor?: string;               // hex string, e.g. "#3E63DD"
  differentiator?: string;            // what makes this segment unique vs others
  performanceMetrics?: {
    users: { value: number; delta: number };
    revenue: { value: number; delta: number };
    retention: { value: number; delta: number };
    aov: { value: number; delta: number };
  };
}
```

Helper function:

```typescript
export function isBehavioralSegment(s: SegmentDisplay): boolean {
  return (s.behavioralTraits?.length ?? 0) > 0;
}
```

## Dependencies & Risks

**Dependencies:**
- Existing `SegmentDisplay` type and `MOCK_SEGMENTS` array
- Existing `SegmentDetailPanel` component (will be conditionally extended)
- Existing push-to-integration flow
- Chat page (`page.tsx`) for "Ask about" navigation target

**Risks:**
- Mock data realism: behavioral segments need convincing LLM-style names and summaries to demo well
- Detail page complexity: conditionally showing/hiding sections in `SegmentDetailPanel` may warrant extracting a `BehavioralDetailPanel` if the branching gets messy
- Chat context injection: reading URL params + sessionStorage on mount is fragile; if the user navigates away and back, context is lost (acceptable for prototype)
